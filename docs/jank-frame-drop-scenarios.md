# 鸿蒙应用丢帧/卡顿：场景与原理

> 配套 `playground/harmony` 的卡顿测试工程（`Jank` story 分类 + `Jank Lab` 页 + `FpsOverlay`）使用。本文讲清楚每一类卡顿**为什么**会丢帧，以及对应示例是怎么把它制造出来的。

## 一、丢帧的本质：一帧没在预算内干完

屏幕以固定刷新率重绘（鸿蒙手机通常 60Hz / 120Hz，即每帧预算 **16.6ms / 8.3ms**）。一帧的流水线大致是：

```txt
vsync 到来 → 事件处理 → 动画计算 → 布局(layout) → 绘制(draw) → 合成 → 上屏
```

只要这条链路上任何一段**总耗时超过一帧预算**，这一帧就来不及上屏，于是**丢一帧**（画面停滞），连续多帧超时就是肉眼可见的"卡顿"。

所以所有卡顿原因归根到底都是同一句话：**主线程在某一帧里干了太多活，或被堵住了；或 GPU/合成阶段超预算。** 不同场景只是"超预算"的方式不同。下面分两大类。

---

## 二、两大类：结构型 vs 时序型

| 类别       | 病因在哪                                                                                   | 载体                                       | 修复思路                                |
| ---------- | ------------------------------------------------------------------------------------------ | ------------------------------------------ | --------------------------------------- |
| **结构型** | 组件树本身太大/太深/载荷太大 → layout、diff 单次就慢                                       | 声明式 JSON 树（树即病因）                 | 瘦树、懒加载、虚拟列表                  |
| **时序型** | 树不大，但**驱动节奏**有问题：阻塞主线程、刷新过频、分块过密、动画驱动方式差、GPU 合成过载 | ArkTS 代码（基准小画面为画布，驱动是病因） | 异步化、节流、用属性动画、降低频率/层数 |

关键区别一句话：**结构型是"一帧内干的活太重"，时序型是"该干的活被安排得不对"。**

> 注意：纯静态的"过度绘制"在 CPU FPS 上看不出来——它要靠**每帧重绘**才显化，所以本工程把 Overdraw 做成时序型（带动画的 ArkUI 原生 Stack），见 §4 第 7 条。

---

## 三、结构型场景（3 个，`Jank` 菜单分类下）

这些是纯 `updateComponents` JSON，点开即渲染。树本身就是卡顿源。

### 1. MassiveTree — 扁平大宽表

**场景**：1 个 `Column` 直接挂 500 个 `Text` 子节点。
**原理**：ArkUI 的布局是自顶向下两遍（measure + layout）。父节点要对**每一个子节点**做 measure，500 个子节点意味着这一帧的 measure 阶段要循环 500 次；若子节点本身还有内在尺寸计算（文本测量），单帧 layout 耗时直接线性膨胀。一次挂载 500 个 → 首帧就爆预算。
**现实对应**：长列表直接 `ForEach` 把全量数据铺成节点（没用 `List`/`LazyForEach` 懒加载）。
**修复**：用 `List` + `LazyForEach`，只 measure 视口内的。

### 2. DeepNesting — 深层嵌套

**场景**：`Column` 嵌 30 层，每层带 3 个 `Text` 兄弟。
**原理**：布局是递归的——每个父节点要先等所有子树 measure 完才能算自己的尺寸，再自顶向下分配位置。嵌套深 → 递归调用栈深 → 单次 layout 的常数项和栈开销大；同时**一处尺寸变化会沿链路向上冒泡、向下回传**多次。
**现实对应**：业务里 `Stack>Column>Row>Column>...` 无脑嵌套。
**修复**：拍平层级，能用 `Flex`/对齐属性解决就别再套一层容器。

### 3. HugePayload — 超大载荷

**场景**：单个 `Text` 的 `text` 字段塞 ~200KB 字符串。
**原理**：卡在**协议解析 + diff 之前**——`SurfaceManager.receiveTextChunk` 收到一条近 200KB 的 JSON，解析（parse）+ 反序列化成组件树 + 与旧树 diff 都得在主线程做完才能进 layout。载荷越大，parse/diff 这一帧越久。
**现实对应**：一次 `updateComponents` 把整页全量重推，而不是只推变化的部分。
**修复**：增量更新（只推 diff）；大文本分块流式推送（SDK 的 streaming 分块机制正是为此）。

> 原计划第 4 个结构型是 Overdraw（半透明层叠加），但 **A2UI 标准组件目录没有 `Stack`/绝对定位组件**，纯声明式 JSON 叠不出真正的过度绘制——做出来的页面是空的。故 Overdraw 改为时序型，用 ArkUI 原生 `Stack` 实现（见 §4 第 7 条）。

## 四、时序型场景（7 个，`Jank Lab` 页按钮）

这些场景共用一个**很小、本该流畅的基准画面**（一个匀速往返色块 + 10 项 List）。卡顿来自 ArkTS 驱动器的**节奏**，不是画面本身。

### 4. MainThreadBlock — 主线程被阻塞

**场景**：`setInterval(100ms)` 里 `while(Date.now() < end){}` 死等 50ms。
**原理**：ArkUI 的渲染跑在主线程。`while` 忙等是纯 CPU 占用，这 50ms 里主线程根本无法处理 vsync、无法推进动画/布局/绘制 → 连续多帧丢失。这是最典型、最致命的卡顿。
**现实对应**：主线程做重计算（大 JSON `JSON.parse`、正则、加密、图片解码）、同步 I/O（`fs.readTextSync`）、忙等待。
**修复**：重活挪到 TaskPool/Worker 子线程；I/O 用异步 API；绝不忙等。

### 5. StateChurn — 高频状态刷新

**场景**：`setInterval(5ms)` 调 `syncState` 刷同一个值。
**原理**：每次状态变更都可能触发依赖该状态的组件标脏 → 重新 measure/layout。5ms 一次刷新意味着主线程每帧都被打断去处理状态 diff，原本一帧预算被切成碎片，渲染管线跑不满。
**现实对应**：滚动事件里 `setState`、传感器/动画 `onValueChange` 里高频改状态没节流。
**修复**：节流（throttle）/ 抖动去重（debounce）；只改真正需要重绘的最小状态；用 `animateTo` 代替手动 setState 驱动动画。

### 6. TinyChunkStream — 过密分块

**场景**：把一条基准 JSON 切成 500 个 ~40 字节小块，`receiveTextChunk` 连推。
**原理**：每收一个 chunk，解析器都要"尝试拼帧 + 判断是否完整 + 触发增量 diff"。分块过密 → 每块几乎都是无意义的中间态，却每次都走一遍 parse+diff 开销 → 主线程被高频小活儿塞满，还伴随画面抖动/闪屏。
**现实对应**：流式协议分块粒度太小（把一条消息按字节切）；或高频 `receiveTextChunk` 推微小更新。
**修复**：合理分块粒度（SDK 的 streaming 默认按 ~10KB / 30 块），别把小载荷再切碎。

### 7. SetTimeoutAnimation — 错误的动画驱动

**场景**：`setInterval(16ms)` 改 `@State` 移动方块，对比 `animateTo` 属性动画。
**原理**：`setInterval(16ms)` 驱动动画有三个问题：① 它不等 vsync，可能在一帧里触发多次或错开 vsync 节拍；② 每次 `@State` 改变都走完整 diff+layout，而非走动画系统的高效插值；③ 主线程一忙，`setInterval` 就被延后，动画"卡顿跳帧"。而 `animateTo` 接在渲染管线的动画系统上，由 vsync 驱动、只插值属性、不触发完整 layout。
**现实对应**：用 `setInterval` / `setTimeout` 手搓动画，而不是 `animateTo` / 属性动画 / `animator`。
**修复**：任何动画用 `animateTo` 或 `animator`，让动画系统按 vsync 节拍插值。

### 8. SurfaceThrash — Surface 抖动

**场景**：循环 `createSurface` → `deleteSurface`。
**原理**：每次 `createSurface` 都要重建 native surface、挂载组件树、首帧 layout；`deleteSurface` 又要拆解释放。频繁抖动 = 反复付"首帧税"，且画面闪退重建。
**现实对应**：路由频繁来回切换、页面被反复 mount/unmount、没复用就销毁。
**修复**：页面复用（keep-alive/缓存）；避免高频 create/destroy。

### 9. MemoryChurn — 内存抖动

**场景**：`setInterval` 每轮分配 ~5MB 数组再丢掉引用。
**原理**：频繁分配大对象 → 堆快速膨胀 → 触发 GC（垃圾回收）。GC 会**暂停主线程**（Stop-The-World 语义），呈**周期性**卡顿（每隔一段时间掉一串帧）。特征是"规律性卡一下"。
**现实对应**：循环里 `new` 大对象/大数组、滚动 cell 反复创建大对象、字符串拼接产生大量中间对象。
**修复**：对象池复用；避免循环内分配；用 `Float64Array` 等定长缓冲；监控堆增长。

> 注意第 9 个的细节：`new Array(N)` 不写元素时是**稀疏数组**，几乎不占内存，反而制造不出 GC 压力——所以本工程里特意 `.fill(0)` 强制分配后端存储，才能真触发 GC 卡顿。这也是个易踩的坑。

### 10. Overdraw — 过度绘制（GPU 合成过载）

**场景**：ArkUI 原生 `Stack` 叠 **200 层**半透明全屏 `Column`，再用 `animateTo` 持续移动一个子元素。
**原理**：过度绘制是**绘制/合成阶段**（GPU）的瓶颈，不在主线程 layout，也不在 CPU。每个像素被 200 层半透明背景反复合成（source-over 混合），GPU 像素填充率被打满。但**静态画面不重绘就没有代价**——所以必须靠 `animateTo` 移动一个子元素**强制每帧重合成整堆层**，overdraw 才会以"GPU 跟不上 vsync → 掉帧"的形式显化。这就是它归时序型而非结构型的原因。
**现实对应**：多层弹窗/遮罩/装饰叠在一起、半透明大背景套半透明大背景，且上面有滚动/动画持续触发重绘。
**修复**：移除不可见层；用不透明 `backgroundColor` 代替半透明叠加；合并图层；开发者选项"过度绘制"调试看红区。
**为什么不在 `Jank` story 菜单**：A2UI 标准目录无 `Stack` 组件，纯 JSON 叠不出真正的层叠；只能用 ArkUI 原生 `Stack` 在 `Jank Lab` 页里演示。

## 五、怎么观察：FPS 与丢帧的度量

光知道原理不够，得能量化。本工程的 `FpsOverlay` 用 `@ohos.graphics.displaySync` 的 `on('frame')` 回调采样：

- **FPS** = 滚动 1 秒窗口内的帧回调数；
- **平均帧时** = 相邻回调时间差的均值；
- **丢帧数** = 回调间隔 > 1.5× 期望帧间隔 的次数。

为什么准？`on('frame')` 回调跑在主线程调度上——**主线程被阻塞时，回调本身就被推迟**。所以回调间隔直接反映主线程真实卡顿，是"应用层体感帧率"，而不是屏幕硬刷新率。

一个边界注意：Overdraw 这类**纯 GPU 合成过载**，主线程可能仍按时收到 vsync 回调，CPU 侧 FPS 不一定掉很多——此时更可靠的观察是 GPU 合成耗时（DevEco Profiler 的 GPU/合成帧），或肉眼可见的动画卡顿。FpsOverlay 仍会因合成器掉帧而出现丢帧计数上升。

判定经验值：稳定 ≥55 视为流畅；30–55 有卡顿感；<30 明显卡顿。

## 七、使用方法速记

- **结构型**：打开 app → 顶栏点亮 `📊 FPS` → 菜单选 `Jank / <场景>` → 看 FPS 掉、看渲染耗时。
- **时序型（含 Overdraw）**：顶栏菜单 → `🧪 Jank Lab` → 选场景按钮 → 看 FPS/丢帧变化 → `Stop` 停 → `animateTo` 看流畅对照。

> 所有时序场景都有 2000 次轮次上限兜底，忘了按 Stop 也不会把页面搞死。Overdraw 不受轮次上限约束（靠 animateTo 驱动，Stop 即停）。
